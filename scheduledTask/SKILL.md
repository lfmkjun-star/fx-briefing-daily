매일 아침 원/달러(USD/KRW) 환율 브리핑을 만들어서 카카오톡으로 보낸다. 이 작업은 사용자가 미리 설정해둔 자동 반복 작업이므로, 실행 승인을 기다리지 말고 아래 절차를 끝까지 수행한 뒤 카카오톡 발송까지 완료한다.

## 1단계 — 환율 숫자 확보 (WebFetch, WebSearch 아님)
WebFetch로 `https://kr.investing.com/currencies/usd-krw` 를 직접 읽어서 "현재 표시된 USD/KRW 환율(현재가)과 전일 종가(Prev. Close), 변동폭, 기준 시각, 52주 최고/최저, 1년 변동률"을 물어본다 (52주 최고/최저와 1년 변동률은 6단계 HTML의 레인지 차트에 쓴다). WebSearch는 숫자 출처로 쓰지 않는다 — 여러 날짜의 캐시된 스니펫이 뒤섞여 서로 안 맞는 값이 나온다는 게 테스트로 확인됨. investing.com을 못 읽거나 전일 대비 변동폭이 비정상적으로 커 보이면, 연합인포맥스나 한국은행 고시환율 페이지를 같은 방식(WebFetch로 단일 페이지 직접 읽기)으로 재시도한다.

주말·공휴일이라 시장이 휴장이면 "직전 거래일 대비"로 계산하고 어느 날짜 기준인지 자연스럽게 문장에 녹인다.

숫자를 못 구하면 지어내지 말고, 카카오톡 메시지에 "오늘 환율 데이터를 가져오지 못했습니다"라고 짧게 보낸다.

## 2단계 — 변동 이유 조사 (WebSearch)
당일 원/달러가 움직인 배경 뉴스를 WebSearch로 찾는다. 키워드 예: 연준(Fed) 발언, 미국 CPI/고용지표, 달러인덱스(DXY), 국내 수출입 수급, 한국은행 정책, 지정학적 이벤트. 로이터·블룸버그·연합인포맥스·매일경제·한국경제 등 신뢰할 수 있는 경제 매체를 우선한다. 뉴스에 근거한 내용만 쓰고, 뚜렷한 재료가 없으면 "특정 이벤트보다는 전반적 달러 강세/약세 흐름에 연동" 정도로 정직하게 쓴다.

실제로 읽은 기사들의 **URL과 매체명, 한 줄 제목, 그리고 기사 내용을 2~3문장으로 요약한 것**을 따로 기록해둔다 — 5단계 카카오톡 링크와 6단계 HTML 근거 기사 항목에 쓸 것이다. 요약은 실제로 읽은 기사 본문에 있는 내용만 담고, 검색 스니펫만 보고 추측해서 채우지 않는다. 검색 결과에 실제로 있던 URL만 기록한다 (지어낸 링크 절대 금지 — 잘못된 링크는 클릭 시 오류/엉뚱한 페이지로 연결되어 신뢰를 해친다).

## 3단계 — 다섯 관점으로 종합
아래 다섯 페르소나의 관점을 순서대로 통과시켜 결론을 벼린다. 최종 메시지에는 페르소나 이름을 절대 노출하지 않는다.
1. 거시/환율 애널리스트 — 금리차, 무역수지, 연준·한은 정책 근거로 "왜"와 "다음 방향"의 1차 초안.
2. 원자재 조달 담당자 — 이 변동폭이 수입 원자재(밀가루, 유지, 포장재 등) 원가에 실질적 영향을 줄 수준인지 판단. 하루 몇 원 변동은 대부분 노이즈임을 인지.
3. 재무·헤지 전략가 — 방향성 전망이 실제 대응(선물환·옵션)할 신호인지, 그냥 지켜볼 수준인지 걸러냄.
4. 리스크 관리자 — 너무 낙관적이거나 한쪽으로 쏠린 전망이 아닌지 반대 시나리오 점검.
5. 가격·마진 전략가 — 결국 원가·가격에 어떤 의미인지, 지금 뭔가 해야 할 수준인지로 마무리.
목적은 다섯 문장을 만드는 게 아니라, 한쪽 관점에만 기대지 않은 균형 잡힌 3줄을 뽑는 것.

## 4단계 — 메시지 작성 및 발송
아래 형식 그대로, 한국어로 3줄을 만든다. 반드시 전체 200자 이내로 맞춘다 (카카오톡 발송 도구 자체가 200자 제한) — 넘으면 "이유" 줄부터 줄인다.

```
📊 변동: [어제/직전 거래일 대비] [▲/▼][N.NN원] ([전일 종가]원 → [오늘]원)
🔍 이유: [당일 주요 재료 1문장]
📈 전망: [단기 방향성 1문장, 확률적 톤] + [짧은 실무 시사점]
```

▲는 원/달러 상승(원화 약세), ▼는 하락(원화 강세)이다. 방향 표시를 헷갈리지 않는다.

완성된 메시지를 `KakaotalkChat-MemoChat` 도구(message 파라미터, 최대 200자)로 즉시 발송한다. 발송 승인을 다시 묻지 않는다 — 이 자동화 자체가 사용자의 사전 승인이다.

## 5단계 — 근거 기사 링크 발송

카카오톡 메시지는 한 통에 200자까지만 들어가므로, 3줄 브리핑과 근거 기사 링크를 한 메시지에 욱여넣지 않는다. 대신 메인 브리핑을 먼저 보낸 뒤, 2단계에서 기록해둔 기사 중 이유·전망 문장에 실제로 반영된 것을 최대 3개 골라 **각각 별도의 카카오톡 메시지로 하나씩** 이어서 보낸다 (총 최대 3통 추가).

각 메시지 형식:

```
🔗 [매체명] 한 줄 제목
URL
```

- URL은 2단계에서 실제로 확인한 것만 쓴다 — 지어내거나 추측한 링크는 절대 보내지 않는다.
- 제목이 길어서 200자를 넘을 것 같으면 제목을 줄인다 — URL이 잘리면 안 된다.
- 서로 다른 매체·다른 관점의 기사가 있으면 같은 이야기를 다루는 기사 여러 개보다 그쪽을 우선한다.
- 조사한 기사가 3개가 안 되면 채워지는 만큼만 보내고, 억지로 3통을 채우지 않는다.
- 각 발송도 승인을 다시 묻지 않는다 — 메인 브리핑과 동일한 자동화의 일부다.

## 6단계 — 상세 HTML 브리핑 갱신 및 링크 발송

카카오톡 3줄 요약과 같은 내용을, 더 상세하게 볼 수 있는 HTML 아티팩트로도 매번 갱신한다. 고정 URL 하나를 계속 덮어써서 "북마크 하나로 매일 최신 내용 보기"가 되게 한다 — 매번 새 아티팩트를 만들지 않는다.

**고정 아티팩트 URL**: `https://claude.ai/artifact/5FPjtyMXbCiRb8f3sDey6D`

절차:
1. `Artifact` 도구를 `action: "read"`, `url: 위 고정 URL`로 호출해 현재 HTML을 읽는다. 이 세션은 이 아티팩트를 발행한 적이 없으므로 반드시 먼저 읽어야 그 위에 발행할 수 있다.
2. 읽어온 HTML의 구조(CSS·레이아웃·톤)는 그대로 두고, 아래 부분만 오늘 데이터로 교체한다:
   - `#genDate` — 오늘 날짜(요일 포함)와 기준 시각
   - `.rate-value` (`#rateValue`) — 오늘 현재가
   - `.delta-pill` (`#deltaPill`) — 방향 화살표·변동폭·%, 그리고 클래스가 `is-up`(원화 약세=상승) 또는 `is-down`(원화 강세=하락)인지도 오늘 방향에 맞게 바꾼다
   - `#rateSub` — "전일 종가 X원 → 오늘 Y원 · 기준" 문장
   - 레인지 차트 SVG — 1단계에서 받은 52주 최저/최고로 좌우 라벨과 마커 위치를 다시 계산한다. 마커 x좌표 = `30 + (오늘값-52주최저)/(52주최고-52주최저)*(570-30)`. 방향에 따라 라인·마커 색을 `var(--up)` 또는 `var(--down)`으로 맞춘다. 마커 아래 텍스트도 오늘 값으로, range-label 하단 문구(52주 구간 내 위치, 1년 변동률)도 갱신한다
   - "오늘 왜 움직였나" 문단 — 2단계 조사 내용을 바탕으로 카카오톡보다 2~4문장으로 조금 더 풀어서 서술 (근거 없는 내용 추가 금지)
   - "다음 며칠 전망" 문단 — 마찬가지로 카카오톡 전망을 2~4문장으로 확장, 확률적 톤 유지
   - `.note` 콜아웃 — 상태 배지(관망/주의/대응 검토 등, 3단계 종합의 결론에 맞게)와 실무 시사점 문장
   - 근거 기사 목록(`.sources`) — 각 `.source-item`은 `.source-head`(매체명 + 제목 링크, 4~5단계 카카오톡과 동일한 매체명·제목·URL)와 그 아래 `.source-summary`(해당 기사 내용을 2~3문장으로 정리한 요약, 2단계에서 기록해둔 것)로 구성한다. 최대 3~4개, 지어낸 링크·지어낸 요약 금지 — 실제로 읽은 기사 내용만 담는다.
3. 수정한 HTML을 `Artifact` 도구로 `action: "publish"`(기본값), `url: 위 고정 URL`, 같은 `file_path`로 다시 발행한다. `favicon`은 이미 설정돼 있으므로 생략한다(재지정하면 안 됨).
4. 발행이 끝나면 카카오톡으로 메시지 한 통을 더 보낸다: `🔗 더 자세히 보기: https://claude.ai/artifact/5FPjtyMXbCiRb8f3sDey6D`. 이 발송도 승인을 묻지 않는다.
5. `read` 단계에서 버전 충돌(다른 곳에서 먼저 수정됨) 오류가 나면, 새로 받은 최신 버전 위에 같은 방식으로 다시 반영해서 발행한다 — force로 덮어쓰지 않는다.
